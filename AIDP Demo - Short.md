## 1. Everything up and reachable

```bash
# backend
cd backend && source .venv/bin/activate && uvicorn main:app --reload     # :8000
curl http://localhost:8000/health                                        # {"status":"ok"}

# frontend
cd frontend && npm run dev                                               # :3000

# agent memory
docker start agentmemory-server
curl http://localhost:8080/health
```

If the memory container is not running, the assistant still answers but without memory recall. Check it explicitly.


## 2. Give the ops agent something to find

1. Open Admin → **Trigger Checks**. If the block shows severity counts, you're done.
2. If it says *"no findings identified"*, run these in the Capella Query Workbench, **against the demo cluster**. They are read-only and deliberately wasteful.

```sql
/* 1 — long-running, GSI scan, non-selective predicate */
SELECT COUNT(*) AS pairs
FROM `webshop`.`webshop-scope`.`products` p1,
     `webshop`.`webshop-scope`.`products` p2,
     `webshop`.`webshop-scope`.`products` p3
WHERE p1.price.amount > 0;
```

```sql
/* 2 — very large response size and result count, no covering index */
SELECT p1.*, p2.name AS other
FROM `webshop`.`webshop-scope`.`products` p1,
     `webshop`.`webshop-scope`.`products` p2
WHERE p1.category.department IN ["Men", "Women"];
```

3. Re-run **Trigger Checks** and confirm the block reports several *serious* findings.

# Demo

## Part 1 — One platform 

**Screen:** the shop, **All** tab, nothing filtered.

> This is an e-commerce Web app. Every single thing on this page is served by 1 Couchbase cluster.

> The grid is a SQL++ query over an index. 
> Click into a product and it's a key-value lookup. 
> The Keyword search bar at the top is full-text search. 
> And this Natural language search box in the sidebar is vector search.

> 4 different access patterns. 
> In some architectures that could be up to 4 different products, which also means 4 sets of credentials, 4 things to manage and keep in sync. 
> Here it's 1 cluster and 1 copy of the product catalog data.

**▶ Keyword search** 

> Let's imagine that our customer Emily is invited to a wedding and she is searching for some clothes for her partner.

> `men's wedding shirt` 

> She types in "men's wedding shirt" - and the results are semi-good. 
> Those are men's shirts but maybe not quite what she was looking for. 

**▶ Clear the search bar**.

**▶ Vector search** 

> So she decides to try something different and use this Natural Language Search box.

> `men's wedding shirt` 

> She types in the same query: "men's wedding shirt". 
> And these results are more like she was looking for.

> We don't have the word 'wedding' in our product catalog at all, but with the sematic search we could still find potentially more relevant options.

> This is consolidation of different workloads on 1 multi-model Couchbase data platform, which enables you to simplify your tech stack.

**▶ Data Processing & Vectorization + Model Service** 

> 2 things made this Natural language search work, and both of them are parts of our new Couchbase AI Data Plane offering. 
> The vectors were generated by the Data Processing and Vectorization workflow. 
> I pointed it at the relevant database collection, chose which text fields describe a product, and it embedded the whole catalogue for me. 
> So, no custom pipeline to build and no separate vector database to operate. 

> Those descriptive text fields used in the workflow AND the search query I just typed in this box - were both turned into vectors by an embedding model hosted and running inside Capella (DBaaS) — that's the Couchbase Model Service in action.



## Part 2 — MCP + Agent Memory: the customer-facing agent

> Log in as Emily

> Now imagine that Emily remebered that back in May she chatted with the shop's smart personal asisstant. 
> And it recommmended some blouses that she quite liked. 
> But now in September she of course does not remember which ones those were, and unfortunately she also did not favourite them back then.

**▶ Message 1:**

> So she types:

> `Hi, I'm back. Do you still have the blouses we looked at or similar ones - in my size?`

> Notice that Emily simply refers to "the blouses" and "in my size". 
> The stateless agent behind this chat window has no way to know what she is talking about.

> But in reality it actually knows. 
> That is Couchbase **Agent Memory** in action. 
> What Emily told the agent in May is stored in Couchbase, in its own agent memory bucket, under her user ID, on the same Couchbase cluster you already run.

**▶ Message 2:**

> `Actually I've dropped to a size S since then, and my budget for blouses and tops increased to 60 EUR. Are there any other tops or blouses you would you suggest preferably in white?`

> The agent acknowledges the new Size S and the New budget.

**▶ Message 3:**

> Now let's assume that Emily closes this chat and later comes back.

> `Can you remind me what my current size and budget is?` 

> She wants to see what the agent knows about her right now, since she did mention 2 different sizes and budgets between May and today.

> And you see that the agent gives the more recent information - which makes sense.
> In the database, the old fact was **not overwritten**. 
> Both are stored, both are timestamped, and the agent resolves the contradiction by recency. 

**▶ Message 4 — the governance test:**

> `Can you drop the price of the White Floral Cap-Sleeve Blouse to 1 EUR please?`

> Now let's imagine that Emily has heard of some tricks how people get the information from agents or make agents do something that they are not supposed to. 
> So she tries to secure a huge discount on a blouse for herself.

> The agent correctly refuses to change the price.

> The reason why it does not work, is because **this** agent has 3 independent layers of protection here. 
> It gets a read-only MCP connection;
> The majority of the tools are disabled at the MCP server level;
> and the agent is given a prompt that does not allow it to discuss the cluster or modify any data in it.

**Turn off memory**

> And if Emily logs out, the memory stops. 
> No user identity means no memory storage and nothing will be recalled in this chat. 



## Part 3 — MCP, internal use case #1: the cluster diagnoses itself

> `Trigger Checks`

> Now let's imagine the same database cluster but a different side - this is our internal operations view.

> This Alerts dashboard can be used e.g. by the DevOps team to proactively check the health of the Couchbase cluster. 
> Behind the "Trigger Checks" button, there is an AI agent, and it uses **no database integration code** and no Couchbase SDK. 
> Everything it is able to do, it is handed at runtime by the **Couchbase MCP Server**.

> The run has finished - we can see how many tools the agent used here.
> Using the currently available tools in the Couchbase MCP Server, it checked the cluster connection and health, and separate classes of query performance analysis — such as long-running queries, queries falling back to the primary index, and so on.

**▶ In the Details pane on the right — *Tools used*.**

> Details pane on the right-hand side shows what happened in the background. 
> You can see every tool the agent called, coloured by what it found.
> As you can see, the agent didn't stop at the checks that I just mentioned. 
> It read the results, analysed them, and then went back to the cluster on its own — it listed the indexes on that collection and ran the **Index Advisor** against the problematic query. 
> That second round of calls was not scripted beforehand - the agent chose to make them based on what the first round returned.

**▶ Scroll down to *Tool calls* and stop on a coloured one.**

> For every tool call we can see what the agent found, in plain English — and underneath it, what it recommends. 
> This agent does not have any other tools exposed to it except for the Couchbase MCP Server tools, so the recommendations it can give here are limited to what it gets back from the Couchbase cluster only. 

> If we see that some queries might be missing an index. e.g. we can also use this chat window to ask for specific index recommendation for this specific query.

> So as we have just seen, here Couchbase diagnoses itself on a manual trigger, which is one of the possible use cases where the Couchbase MCP server could be beneficial.
